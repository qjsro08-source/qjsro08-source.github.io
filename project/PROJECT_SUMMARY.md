# 한국어 육아 QA 도메인 특화를 위한 Gemma 4 E4B LoRA 파인튜닝

> 이력서·포트폴리오·면접 설명을 위한 프로젝트 정리 문서입니다. 현재 코드, 데이터 파일, 저장된 어댑터와 학습 로그를 근거로 작성했습니다.
>
> 현재 상태: 데이터 전처리 및 LoRA 학습·저장 완료. 학습 전후 응답 비교 코드 구현. 응답 품질 평가, SFTTrainer 전환, PTQ는 후속 과제입니다.

## 1. 이력서에 바로 사용할 요약

### 프로젝트 소개

**한국어 육아 QA 도메인 특화를 위한 LLM 파인튜닝 파이프라인 구현**

범용 한국어 QA 데이터에서 육아 관련 질문·답변을 선별하고, 채팅 템플릿 적용과 답변 전용 라벨 마스킹, 동적 패딩을 구현하여 Gemma 4 E4B 모델의 LoRA 학습 및 어댑터 저장까지 수행한 프로젝트.

**기술 스택:** Python, PyTorch, Hugging Face Transformers·Datasets, PEFT, pandas, Apple MPS

### 주요 구현 및 성과

- 한국어 QA **131,327건**을 공통 스키마로 통합하고, 도메인 키워드·오탐 제외·길이 필터·질문 중복 제거를 적용해 **육아 QA 427건** 구축.
- 채팅 템플릿의 프롬프트 토큰 경계를 검증하고, 질문·패딩 영역을 `-100`으로 마스킹하는 **답변 전용 학습 데이터 처리 및 동적 패딩 Collator 구현**.
- Apple MPS 환경에서 bf16 베이스 모델에 **LoRA 적용 및 3 epoch·129 step 학습 완료**. 저장된 어댑터 파라미터는 **4,538,368개**.
- 검증셋 42건에 대한 **validation loss를 1 epoch 종료 시 2.126에서 3 epoch 종료 시 1.946으로 약 8.4% 감소**시켰으며, 동일 모델에서 어댑터 활성화 여부에 따른 응답 비교 코드 구현.

### 공간이 적을 때 사용할 2문장 버전

한국어 QA 13.1만 건에서 육아 데이터 427건을 선별하고, 답변 전용 라벨 마스킹과 동적 패딩을 구현해 Gemma 4 E4B의 LoRA 학습 파이프라인을 구축했습니다. Apple MPS에서 3 epoch 학습을 완료했으며, 검증 손실은 1 epoch 종료 시 2.126에서 3 epoch 종료 시 1.946으로 감소했습니다.

성과 수치의 비교 기준은 **1 epoch 종료 시점과 3 epoch 종료 시점**입니다. 미학습 베이스 모델 대비 개선율이나 답변 정확도 개선율을 의미하지 않습니다.

## 2. 프로젝트 목표와 범위

범용 한국어 QA 데이터에서 특정 도메인에 필요한 데이터를 구성하고, LLM 학습 입력과 정답 라벨을 직접 제어하며 파라미터 효율적 파인튜닝 과정을 구현하는 것이 목표입니다.

| 항목 | 내용 |
|---|---|
| 대상 도메인 | 한국어 육아·임신·출산·영유아 관련 QA |
| 베이스 모델 | `google/gemma-4-E4B-it` — 현재 설정 및 어댑터 메타데이터 기준 |
| 학습 방식 | PEFT LoRA를 이용한 지도 파인튜닝 |
| 구현 범위 | 데이터 로딩·탐색·정제·분할, 토큰화·라벨 구성, 배치 처리, 학습, 어댑터 저장, 추론 비교 코드 |
| 현재 실험 환경 | 로컬 Mac, Apple MPS |
| 후속 목표 | 응답 품질 평가, SFTTrainer와 직접 구현한 라벨 대조, PTQ 및 RTN 비교 |

현재 구현은 텍스트 QA를 대상으로 합니다. 모델의 멀티모달 기능, RAG, 웹 서비스, 배포 시스템은 구현 범위에 포함하지 않았습니다.

## 3. 전체 처리 흐름

```text
KoAlpaca + Korean QA Dataset
             │
             ▼
공통 스키마 통합 + Human:/GPT: 접두사 제거
             │
             ▼
육아 키워드 포함 / 오탐 단어 제외
             │
             ▼
결측·빈 문자열·길이 검사 + 동일 질문 중복 제거
             │
             ▼
train / valid / test 분할 — seed 42
             │
             ▼
채팅 템플릿 적용 + 토큰화 + 질문 라벨 마스킹
             │
             ▼
동적 패딩 Collator → Transformers Trainer → PEFT LoRA
             │
             ▼
어댑터·토크나이저·채팅 템플릿 저장
             │
             ▼
어댑터 활성화/비활성화 응답 비교 코드
             │
             └─ 후속 과제: 평가 결과 저장·분석 → PTQ 실험
```

단계 간 결과를 Parquet·JSONL 파일로 전달합니다. 각 처리 함수가 직전 단계의 파일을 읽으므로, 앞 단계 전체를 재실행하지 않고 특정 단계부터 다시 실행할 수 있습니다.

## 4. 데이터 구성과 전처리

### 4.1 원본 데이터와 스키마 통합

| 데이터셋 ID | 원본 행 수 | 원본 질문·답변 컬럼 | 공통 `source` 값 |
|---|---:|---|---|
| `beomi/KoAlpaca-v1.1a` | 21,155 | `instruction`, `output` | `koalpaca` |
| `IkJun1/korean-qa-dataset` | 110,172 | `prompt`, `response` | `synthetic` |
| 합계 | **131,327** | — | — |

공통 스키마는 `question`, `answer`, `source`입니다. 합성 데이터의 질문·답변 앞에 붙은 `Human: `, `GPT: `를 제거하고, 전처리 후 접두사가 남지 않았는지 assertion으로 검사합니다.

`source`를 유지해 추후 데이터 출처별 평가와 실제 QA·합성 QA 구성에 따른 실험이 가능하도록 했습니다. 현재 두 출처를 분리해 학습한 비교 실험은 없습니다.

### 4.2 도메인 필터와 정제

질문에 `육아`, `이유식`, `모유`, `수유`, `신생아`, `임신`, `출산` 등 **24개 키워드** 중 하나가 포함되는지 검사합니다. `아이`처럼 오탐이 발생하기 쉬운 단어에 대응해 `아이디`, `아이템`, `아이폰`, `아이스크림` 등 제외어를 별도로 적용합니다.

| 단계 | 남은 행 수 | 처리 내용 |
|---|---:|---|
| 통합 | 131,327 | 컬럼 통일 및 접두사 제거 |
| 포함 키워드 적중 | 863 | 질문 기준 도메인 키워드 탐색 |
| 제외어 적용 | 468 | 포함 키워드 적중 건 중 395건 제거 |
| 결측·빈 문자열·길이 필터 | 468 | 현재 데이터에서는 추가 제거 0건 |
| 동일 질문 중복 제거 | **427** | 41건 제거, 답변이 가장 긴 행 유지 |

문자 수 기준은 질문 **10~1,000자**, 답변 **30~3,000자**입니다. 정제 후 질문 길이는 중앙값 56자·최대 623자, 답변 길이는 중앙값 294자·최대 1,173자입니다.

답변 길이를 기준으로 중복을 제거한 것은 일관된 선택 규칙을 두기 위한 결정입니다. 긴 답변의 사실성이나 정확성이 더 높다는 것을 검증한 것은 아닙니다.

### 4.3 데이터 분할

`seed=42`로 전체 데이터를 섞은 뒤 80%·10%·나머지 비율로 분할했습니다. 출처별 층화 분할은 적용하지 않았습니다.

| 분할 | KoAlpaca | 합성 데이터 | 합계 |
|---|---:|---:|---:|
| Train | 197 | 144 | **341** |
| Validation | 22 | 20 | **42** |
| Test | 25 | 19 | **44** |
| 합계 | **244** | **183** | **427** |

저장된 세 JSONL 파일에서 **동일 문자열 질문의 분할 간 중복은 0건**입니다. 의미가 유사한 질문까지 분리했는지는 별도로 검증하지 않았습니다.

근거: [전처리 코드](src/data/preprocessing.py), [데이터 탐색 코드](src/data/explore.py), `data/interim/*.parquet`, `data/processed/*.jsonl`.

## 5. 학습 데이터와 라벨 처리

### 5.1 채팅 템플릿

저장된 토크나이저로 확인한 단일 QA의 렌더링 형식은 다음과 같습니다. 아래 `\n`은 줄바꿈을 나타냅니다.

```text
학습 입력:
<bos><|turn>user\n질문<turn|>\n<|turn>model\n답변<turn|>\n

추론 입력:
<bos><|turn>user\n질문<turn|>\n<|turn>model\n
```

메시지의 `assistant` 역할은 템플릿에서 `model`로 바뀝니다. 학습 라벨에는 답변뿐 아니라 종료를 나타내는 `<turn|>`와 뒤따르는 줄바꿈도 포함합니다.

`chat_template.jinja`는 대화의 직렬화 형식을 정의하며, 학습 마지막에 `tok.save_pretrained()`로 토크나이저와 함께 저장됩니다. 직접 구현한 핵심 부분은 `src/lora/dataset.py`의 라벨 마스킹과 Collator입니다.

### 5.2 답변 전용 라벨 마스킹

1. 질문과 답변 전체를 토큰화해 `input_ids`를 만듭니다.
2. 질문과 답변 시작 헤더만 토큰화해 프롬프트 길이를 계산합니다.
3. 프롬프트 토큰 배열이 전체 토큰 배열의 정확한 접두사인지 검사합니다.
4. 전체 토큰 배열을 복사한 뒤, 프롬프트 위치의 `labels`만 `-100`으로 변경합니다.
5. 질문은 입력 문맥으로 유지하면서 답변 영역에만 loss가 계산되도록 합니다.

문자열의 접두사 관계만 확인하지 않고 **실제 토큰 배열도 비교**해 토큰화 경계가 달라졌을 때 즉시 중단하도록 구현했습니다. 또한 `return_dict=False`를 명시해 토큰 ID 리스트를 받도록 했습니다.

현재 저장된 템플릿에는 `{% generation %}` 블록이 없어, 해당 블록에 의존하는 assistant 영역 자동 마스크 대신 프롬프트 길이에 기반한 직접 마스킹을 사용합니다.

### 5.3 길이 정책과 동적 패딩

토큰화한 전체 길이가 **1,024 토큰을 초과하는 예제는 제외**하도록 구현했습니다. 답변을 중간에서 잘라 종료 부분을 잃는 상황을 피하기 위한 정책입니다. 앞의 데이터 분할 표는 토큰 길이 필터 이전 JSONL 기준입니다.

Collator는 배치에서 가장 긴 시퀀스에 맞춰 오른쪽 패딩을 적용합니다.

| 항목 | 패딩 값 | 역할 |
|---|---|---|
| `input_ids` | `pad_token_id` = `0` | 입력 시퀀스 길이 정렬 |
| `labels` | `-100` | 패딩 위치를 loss에서 제외 |
| `attention_mask` | `0` | 패딩 위치 표시; 실제 입력은 `1` |

현재 학습 배치 크기는 1이므로, 여러 길이의 샘플을 함께 묶을 때의 동적 패딩 효율 향상은 이번 학습에서 측정하지 않았습니다. Collator에는 배치 크기를 늘렸을 때도 사용할 수 있는 처리가 구현되어 있습니다.

근거: [학습 데이터 처리 코드](src/lora/dataset.py), [저장된 채팅 템플릿](outputs/adapters/final/chat_template.jinja).

## 6. LoRA 학습 구성

### 6.1 하이퍼파라미터

| 항목 | 설정 |
|---|---|
| 베이스 모델 | `google/gemma-4-E4B-it` |
| 베이스 모델 로딩 dtype | `torch.bfloat16` |
| 학습 장치 | `mps` |
| LoRA rank / alpha | `16` / `32` |
| LoRA dropout | `0.05` |
| 실제 적용 모듈 | 언어 모델의 `q_proj`, `v_proj` |
| Bias / task type | `none` / `CAUSAL_LM` |
| Epoch | `3` |
| 학습률 | `1e-4` |
| 장치당 학습 batch size | `1` |
| Gradient accumulation | `8` |
| 단일 장치 기준 명목 유효 배치 | `8`개 예제; 마지막 누적 구간은 더 작을 수 있음 |
| Warmup / scheduler | `warmup_ratio=0.03` / cosine |
| Gradient checkpointing | 사용, `use_reentrant=False` |
| 모델 KV cache | 학습 시 `use_cache=False` |
| 평가·저장 주기 | 매 epoch |
| 체크포인트 보관 수 | 최근 2개 |
| 로그 기록 | 5 step마다 |
| Seed | `42` |

코드에서는 `target_modules=None`으로 두고 PEFT의 모델별 기본 선택을 사용했습니다. 저장된 `adapter_config.json`에서 실제 대상이 `.*language_model\..*\.(q_proj|v_proj)`임을 확인했습니다. 적용 대상을 직접 탐색해 최적화한 실험은 수행하지 않았습니다.

`r=16`, `alpha=32`, 학습률 `1e-4`는 현재 실험의 설정값입니다. 여러 후보를 비교해 최적값임을 입증한 결과는 없습니다.

### 6.2 자원 사용을 고려한 구현

- **LoRA:** 베이스 모델의 전체 파라미터 대신 추가한 어댑터 파라미터를 학습합니다.
- **bf16 베이스 모델 로딩:** 학습 코드에서 모델 가중치의 로딩 dtype을 지정합니다.
- **Gradient accumulation:** 장치당 배치 1로 여러 마이크로배치의 gradient를 누적합니다.
- **Gradient checkpointing:** 중간 activation을 다시 계산하는 방식을 사용합니다.
- **KV cache 비활성화:** 학습 시 모델 cache를 사용하지 않도록 설정합니다.

이 설정들을 적용해 학습을 완료했습니다. 각 설정에 따른 메모리 절감량·처리 속도의 비교 측정 기록은 없습니다.

### 6.3 저장된 어댑터

| 항목 | 확인 결과 |
|---|---:|
| 저장된 텐서 수 | 132개 |
| 어댑터 파라미터 수 | **4,538,368개** |
| 어댑터 가중치 파일 크기 | **18,173,080 bytes**, 약 **17.33 MiB** |
| 저장된 어댑터 텐서 dtype | **F32** |

파라미터 수와 dtype은 `adapter_model.safetensors`의 헤더를 읽어 확인했습니다. bf16 베이스 모델 로딩과 어댑터의 실제 저장 dtype은 구분해야 합니다. 위 파일 크기는 어댑터 가중치만의 크기이며, 추론에 필요한 베이스 모델과 토크나이저의 크기는 포함하지 않습니다.

근거: [학습 코드](src/lora/train.py), [어댑터 설정](outputs/adapters/final/adapter_config.json), `outputs/adapters/final/adapter_model.safetensors`.

## 7. 확인된 실험 결과

### 7.1 Validation loss

| Epoch 종료 시점 | Global step | Validation loss |
|---|---:|---:|
| 1 | 43 | 2.125532 |
| 2 | 86 | 1.957085 |
| 3 | 129 | **1.946263** |

1 epoch 종료 시점 대비 3 epoch 종료 시점의 validation loss 감소율은 다음과 같습니다.

```text
(2.1255321503 - 1.9462629557) / 2.1255321503 × 100 ≈ 8.43%
```

기록된 세 번의 평가 중 마지막 epoch의 loss가 가장 낮았습니다. 코드에 최적 체크포인트를 자동 선택해 다시 로드하는 설정은 없으며, `final/`에는 학습 종료 시점의 어댑터를 저장합니다.

### 7.2 결과의 해석 범위

- 저장된 학습 로그로 **3 epoch·129 step 완료 및 validation loss 감소**를 확인할 수 있습니다.
- 학습 시작 전 베이스 모델의 validation loss가 기록되어 있지 않아, 베이스 모델 대비 손실 개선율은 계산할 수 없습니다.
- Test 44건 전체에 대한 정량 평가와 저장된 응답 품질 비교 결과는 없습니다.
- 현재 결과만으로 육아 답변의 정확성·유용성 개선, 일반 능력 유지, 과적합 여부를 확정할 수 없습니다.
- 동일 설정의 반복 실험이나 여러 seed에 대한 변동성 분석은 수행하지 않았습니다.

근거: [3 epoch 학습 로그](outputs/adapters/checkpoint-129/trainer_state.json).

## 8. 추론 비교 구현

`infer.py`는 동일한 베이스 모델에 저장된 어댑터를 연결한 뒤, 어댑터를 끄거나 켜서 응답을 비교하도록 구현되어 있습니다.

| 항목 | 현재 구현 |
|---|---|
| 모델 로딩·추론 장치 | CPU |
| dtype | float32 |
| 비교 방법 | `model.disable_adapter()` 사용 여부 |
| 입력 질문 | Test 데이터 앞 3건 + 파이썬 리스트·튜플 차이 질문 1건 |
| 생성 설정 | `do_sample=False`, `max_new_tokens=80` |
| 출력 | 프롬프트 이후 생성된 토큰만 디코딩, 특수 토큰 표시 |

육아 질문과 일반 질문을 함께 배치해 도메인 응답 변화와 일반 능력 변화를 살펴볼 수 있게 구성했습니다. 다만 비교 코드 구현과 평가 완료는 구분해야 하며, 현재 저장된 결과 파일은 없습니다. 80 토큰 제한은 긴 답변을 중간에 끊을 수 있으므로 후속 평가에서 종료 여부를 함께 확인할 필요가 있습니다.

근거: [추론 비교 코드](src/lora/infer.py).

### 11.2 실행 순서

프로젝트 루트에서 가상환경 Python으로 모듈을 실행합니다. 아래 명령은 실행 안내이며, 문서 작성 중 전처리·학습·모델 추론을 다시 수행한 것은 아닙니다. 전처리와 학습 명령은 해당 경로의 산출물을 다시 생성합니다.

```bash
# 1. 데이터 관찰
.venv/bin/python -m src.data.explore

# 2. 데이터 통합·필터·정제·분할
.venv/bin/python -m src.data.preprocessing

# 3. 토큰화·라벨 마스킹·배치 구조 확인
.venv/bin/python -m src.lora.dataset

# 4. LoRA 학습 및 저장
.venv/bin/python -m src.lora.train

# 5. 어댑터 적용 전후 응답 비교
.venv/bin/python -m src.lora.infer
```

원본 데이터와 베이스 모델은 로컬 캐시가 없다면 다운로드가 필요합니다. 학습 장치가 `mps`로 지정되어 있으므로 NVIDIA 환경으로 옮길 때는 장치 설정을 조정해야 합니다.

### 11.3 재현성 관점의 현재 상태

- 경로·모델 ID·seed는 `config.py`에 모여 있습니다. 학습 하이퍼파라미터는 `train.py`에 있습니다.
- 데이터 분할과 Trainer의 seed를 고정했고, 단계별 중간 데이터를 저장합니다.
- 의존성 버전을 고정하는 `requirements.txt` 또는 lock 파일은 아직 없습니다.
- 모델·데이터 revision을 고정하지 않아 외부 저장소 변경까지 통제하지는 않습니다.
- 추론에서도 `src/lora/dataset.py`의 토크나이저를 가져오므로, 현재는 `final/`에 저장된 토크나이저 대신 `config.MODEL_ID`에서 로드합니다. 저장된 템플릿만 수정해도 기존 추론 코드에는 직접 반영되지 않습니다.
- `infer.py`의 어댑터 dtype 주석과 실제 저장된 F32 텐서 사이에 차이가 있습니다. 문서의 dtype 설명은 실제 파일을 기준으로 작성했습니다.
- `CLAUDE.md`의 진행 체크리스트에는 학습 단계가 미완료로 남아 있지만, 코드와 저장된 체크포인트는 학습 완료를 보여줍니다.

## 13. 면접에서 설명할 핵심

### 1분 소개 예시

> 범용 한국어 QA 데이터를 육아 도메인에 맞게 선별해 Gemma 4 E4B 모델을 LoRA로 학습한 프로젝트입니다. 두 데이터셋의 약 13만 건을 통합한 뒤 키워드 필터, 오탐 제외, 길이 검사, 중복 제거를 거쳐 427건을 구성했습니다. 질문은 입력 문맥으로 남기되 답변에만 loss가 계산되도록 라벨을 직접 만들었고, 토큰화 경계와 패딩 처리를 검증하는 코드를 작성했습니다. Apple MPS에서 3 epoch 학습을 완료했으며, 검증 손실은 1 epoch 종료 시 2.126에서 3 epoch 종료 시 1.946으로 감소했습니다. 현재는 어댑터 적용 전후 비교 코드를 구현한 상태이며, 다음 단계는 동일 기준의 응답 평가와 PTQ 실험입니다.

### 예상 질문과 답변 근거

| 질문 | 답변할 핵심 |
|---|---|
| 왜 LoRA를 사용했나요? | 로컬 환경에서 베이스 모델을 유지하면서 일부 추가 파라미터만 학습하는 방식을 실습하기 위해 사용했습니다. 저장된 어댑터는 약 454만 파라미터입니다. |
| 질문 라벨을 왜 마스킹했나요? | 질문을 입력 문맥으로 읽게 하면서, 답변 생성에 대한 학습 신호만 주기 위해서입니다. 입력 토큰은 유지하고 라벨만 `-100`으로 변경했습니다. |
| 마스킹이 맞는지 어떻게 확인했나요? | 문자열과 토큰 배열의 접두사 관계를 검사하고, 마스킹되지 않은 라벨에 해당하는 토큰을 디코딩해 답변과 종료 부분이 남는지 확인하도록 구현했습니다. |
| padding token과 `-100`은 어떻게 다른가요? | pad token은 입력의 길이를 맞추는 토큰이고, `-100`은 해당 위치를 loss 계산에서 제외하는 라벨 값입니다. |
| 데이터 누수는 어떻게 확인했나요? | 분할 전에 동일 질문을 제거했고, 저장된 split 사이에 동일 문자열 질문이 없는지 확인했습니다. 의미상 유사 질문 누수까지 배제했다고 주장하지는 않습니다. |
| `r=16`, `alpha=32`가 최적인가요? | 현재 실험에 사용한 시작 설정입니다. 후보별 비교 실험을 하지 않았기 때문에 최적값이라고 판단하지 않았습니다. |
| 약 8.4% 개선은 무엇을 의미하나요? | 1 epoch와 3 epoch 종료 시점의 validation loss 상대 감소율입니다. 답변 정확도나 미학습 베이스 모델 대비 개선율은 아닙니다. |
| 프로젝트의 가장 큰 한계는 무엇인가요? | 데이터가 작고, 정량 지표가 validation loss에 한정돼 있습니다. 베이스 모델과의 실제 답변 비교 결과를 저장하고 평가하는 작업이 남아 있습니다. |
